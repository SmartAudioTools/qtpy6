## 3. Les choix, et ce qui a été écarté

### 3.1 Doublures dans les modules Qt de qtpy6, plutôt qu'une bibliothèque à importer

- **Choix** : c'est `qtpy6.QtCore` qui pose les doublures au chargement, sur les classes de PyQt6 elles-mêmes (c'est ce
  que j'appelle « loger les remplacements Qt »).
- **Pourquoi** : c'est la demande même (« un seul import qtpy6 »). En plus, une doublure posée sur la classe PyQt6 couvre
  aussi le code qui importe `PyQt6` directement, ainsi que les sous-classes de l'application.
- **Risque à relire** : c'est un monkey-patching global de PyQt6. Il est limité au navigateur, où nous sommes le seul
  code Qt présent.

### 3.2 Suspension par JSPI, plutôt qu'une réécriture de l'application en asynchrone

- **Choix** : `exec()` suspend réellement la pile WebAssembly (`pyodide.ffi.run_sync`), puis rend sa valeur comme en
  natif.
- **Écarté** : demander aux applications de passer en `open()` + signaux. Cela contredit « application non modifiée ».
  C'est ce que faisait jusqu'ici le lecteur de SmartTeacher, qui reste compatible.
- **Contrainte** : `run_sync` ne marche que dans une entrée « promettante » (le script principal lancé par
  `runPythonAsync`, ou une tâche asyncio). Un slot que Qt appelle depuis le C++ n'en est pas une. D'où le point suivant.

### 3.3 Report des slots à la tâche asyncio suivante

- **Choix** : `SignalInstance.connect` est doublé. Le slot Python est enveloppé dans un relais :
  - si l'appel peut suspendre, le slot est exécuté sur place ;
  - sinon, il est reporté par `call_soon`.
- **Ce qui est préservé** :
  - `sender()` : une pile `_expediteur` le rend pendant le slot reporté ;
  - le nombre d'arguments que le slot accepte (`_nb_arguments`) ;
  - un seul relais par slot (`WeakValueDictionary`, clé `(id(self), fonction)` pour une méthode liée) : PyQt y
    reconnaît un doublon (`UniqueConnection`) et le retrouve (`disconnect(slot)`), et c'est la connexion qui le garde
    en vie, pas la table (révisé après la vérification, section 9) ;
  - la durée de vie du receveur : référence faible, et `sip.isdeleted` vérifié.
- **Exception** : `destroyed` est toujours direct. Reporté, l'objet serait déjà mort.
- **Point délicat, à relire** : `can_run_sync()` **ment** tant qu'une autre pile est suspendue. Il répond `True`, mais le
  `run_sync` ne reprend jamais : mesuré, ni retour ni erreur. `bloquant` tient donc sa propre comptabilité
  (`_actif`, `_suspendus`, dans `_peut_suspendre`, `_suspendre` et `_plus_tard`). La cohérence de ces deux variables
  est LE point à vérifier. En particulier la ligne `_actif = avant or _suspendus > 0` à la reprise.
- **Conséquence voulue** : un slot reporté s'exécute un tour plus tard qu'en natif. Du code qui compte sur l'ordre exact
  « émission puis effet du slot dans le même appel » pourrait voir une différence. Le code Python qui émet lui-même
  (`emit`, `click()`) reste immédiat, parce qu'il tourne déjà dans une entrée suspendable.

### 3.4 `QTimer.singleShot(ms, fonction)` relayé (ajouté en dernier)

- **Constat en direct dans Firefox** : une `QMessageBox.exec()` dans un `singleShot` ne bloquait pas. Qt appelle la
  fonction depuis le C++ sans passer par `connect`.
- **Correctif** : `QTimer.singleShot` est doublé. Son dernier argument, s'il est un appelable Python, passe par le même
  `relayer`. Le doublage se superpose à celui de qtpy6 pour la forme PySide6 à trois arguments.
- **Test** : `test_un_coup_de_minuterie_est_un_slot` attend « rendu 7 ». Vérifié qu'il ÉCHOUE sans le correctif : il
  rend alors « rendu 0 ».
- **Piège évité** : la simulation des tests utilise elle-même `QTimer.singleShot` (la même classe). Elle capture donc
  l'original (`_un_coup`) avant que qtpy6 ne le double.

### 3.5 La pompe `processEvents`

- **Constat mesuré** : compilé avec JSPI, Qt-WASM n'envoie ni minuteries ni événements postés de lui-même.
  `qeventdispatcher_wasm.cpp`, `onTimer` : `if (useAsyncify()) return;`. Un `QTimer` ne partait que tant que la page
  redessinait.
- **Choix** : un `setInterval` JS de 10 ms qui appelle `processEvents()`.
- **Démarrée au chargement de `QtCore`**, pas dans `exec()`. Première version : dans `exec()` et dans `application()`,
  deux endroits. Simplifiée à un seul, parce qu'une application sans `exec()` (qui se contente de montrer une fenêtre)
  doit aussi voir ses minuteries tourner. Vérifié dans Firefox avec une application sans `exec()` : 20 tics comptés.
- **À relire** : 10 ms est une valeur choisie, pas optimisée (charge CPU, batterie d'un téléphone). `processEvents` est
  appelé depuis une entrée non promettante : les slots y sont donc reportés, et rien ne suspend au milieu.

### 3.6 Fils coopératifs (`fils.py`)

- **Choix** :
  - `QThread.start()` lance `run()` à la tâche asyncio suivante ;
  - `msleep`, `wait`, `QWaitCondition.wait`, `QSemaphore.acquire`, `QMutex.lock` et `time.sleep` suspendent
    (`_pause`, `_attendre`) ;
  - `moveToThread` ne fait rien, et les signaux entre fils deviennent des appels directs ;
  - un verrou ou un sémaphore qu'on ne peut pas obtenir hors entrée suspendable lève `RuntimeError` au lieu de figer
    la page (vrai seulement pour `QSemaphore` avant la vérification, section 9). Dans une entrée suspendable, un
    interblocage réel fige la tâche en attente, pas la page, et rien ne le signale.
- **Écarté** : de vrais fils (pthreads WASM). Ils demandent `SharedArrayBuffer` et les en-têtes COOP/COEP, donc plus
  d'hébergement statique nu. Pyodide-Qt n'est de toute façon pas compilé ainsi.
- **Détail mesuré** : `started` était émis avant `exec()`, ce qui laissait le `quit()` d'un travailleur rapide passer
  devant (`wait()` rendait `False`). `started` est maintenant émis à la tâche suivante.
- **Limites** :
  - un `run()` qui calcule sans jamais attendre garde la main jusqu'au bout ;
  - `threading.Thread` et `multiprocessing` ne sont pas doublés.

### 3.7 `QProcess` → Web Worker

- **Choix** : dans le navigateur, `qtpy6.QtCore.QProcess` EST `ProcessusWeb` : `start`, `write`,
  `readAllStandardOutput`, `kill`, les signaux, et les alias snake_case.
- **Ce qui change pour l'application** : ce qui tournait dans le sous-processus devient un module importé par le worker
  (`travailleur.configurer`). C'est le seul changement de code demandé à une application qui lance un sous-processus.
- **Deux Pyodide** : la page tourne sous Pyodide-Qt (Python 3.13), le worker sous un Pyodide ordinaire (Python 3.14).

### 3.8 Police fixe par `QFontDatabase.systemFont(FixedFont)`

- **Choix** : doubler l'API Qt standard plutôt que garder `qtpy6web.police_fixe()`. Le code applicatif reste celui du
  bureau. Côté SmartTeacher, `console_code.py` et `editeur_code.py` ont été passés à `systemFont`.
- **Mécanisme** : `addApplicationFont` est doublé pour noter les familles chargées. La première à chasse fixe est
  rendue, à la taille de la police de l'interface.

### 3.9 `construire` / `lancer`

- **`lancer(script)`** exécute le script comme `python script` :
  - `__name__ == "__main__"`, `sys.argv`, `sys.path` et le dossier courant sont posés ;
  - `SystemExit` est rattrapé et donne le code de retour ;
  - `pret()` est appelé quand l'application entre dans `exec()`, sinon à la fin du script.
- **`construire`** prend tout le dossier du script, sauf les fichiers cachés, `__pycache__` et le site lui-même.
  - Par défaut, la page charge Pyodide-Qt depuis `https://smartaudiotools.github.io/qtpy6/pyodide-qt/`. **Cette URL
    n'est pas encore en ligne** : l'hébergement actif est toujours celui de l'ancien dépôt qtpy6web.
  - Publier les Pages de qtpy6 (`hebergement/telecharger.sh`, `pages.yml`) revient à l'utilisateur.

### 3.10 Côté SmartTeacher et SmartOS

- Les imports sont passés de `qtpy6web` à `qtpy6.web`, ainsi que la doc (`CLAUDE.md`, `QCM/README.md`, la note
  « Déploiement web d'un sujet ») et la sonde (`python -m qtpy6.web.sonde`).
- **Gardés tels quels, volontairement** :
  - le nom de fichier `qtpy6web.js` (le chargeur) ;
  - les notes historiques (DONE, Plan lecteur web) ;
  - les URL d'hébergement de `page.html` et `index.html`, qui pointent toujours vers l'ancien dépôt, encore en service.
- **SmartOS** : la ligne `-e /DATA/Python/qtpy6web` est retirée des deux requirements de SmartPython. qtpy6 y était déjà.

## 5. Limites connues (aussi dans `web.md`, « Rendre une application qtpy6 compatible »)

1. **`exec()` dans une méthode virtuelle** (`contextMenuEvent`, `mousePressEvent`, `closeEvent`…) : rien ne peut y
   suspendre. La boîte s'ouvre sans bloquer, rend la valeur d'un abandon et affiche un avertissement, une seule fois.
   Contournement : `QTimer.singleShot(0, …)`.
2. **Un `exec()` lancé par Qt en C++** (le menu d'un `QToolButton`, `showMenu()`) ne bloque pas.
3. **Calcul long sans attente** : il fige la page. `threading.Thread` et `multiprocessing` ne sont pas doublés.
4. **Fichiers** : ils sont en mémoire et perdus au rechargement. Ce qui doit survivre passe par `stockage`.
5. **Pas d'arguments nommés de propriété** dans les constructeurs (limite de PyQt6).

## 7. Ce que je demanderais à un relecteur de vérifier en priorité

1. **La comptabilité `_actif` / `_suspendus` de `bloquant.py`.** Peut-il arriver qu'un slot s'exécute sur place alors
   qu'une pile est suspendue (blocage silencieux), ou soit reporté indéfiniment ? Cas à regarder : deux boîtes
   imbriquées (une boîte ouverte depuis un slot d'une autre), une boîte fermée pendant qu'une autre attend, une
   exception dans un slot reporté.
2. **Le relais de `connect`** : fuite mémoire de la table `relais`, dont les entrées mortes ne sont nettoyées qu'au
   `disconnect` ; `disconnect()` sans argument ; `connect` avec `Qt.ConnectionType` ; slots décorés `@Slot` ;
   `functools.partial` ; lambdas.
3. **`QTimer.singleShot` doublé** : les formes `singleShot(ms, receveur, slot)` et `singleShot(ms, TimerType, fonction)`,
   et la cohabitation avec le doublage PySide6 de qtpy6 (`_singleShot_with_receiver`).
4. **`menu_exec`** : attendre un tour après `aboutToHide`, parce que `triggered` part après, dans le même appel. Est-ce
   robuste ?
5. **`fils.py`** : la sémantique de `QMutex`, `QWaitCondition` et `QSemaphore` sur un seul fil, et la détection
   d'interblocage.
6. **Les tests simulés reflètent-ils le vrai JSPI ?** greenlet n'a pas le mensonge de `can_run_sync`. La simulation
   pourrait être plus permissive que le navigateur.
7. **L'URL par défaut de `construire`** pointe vers un hébergement pas encore publié.
8. **La cadence de la pompe** (10 ms) et son coût sur un téléphone.

## 9. Première vérification des huit points, par Claude lui-même (27/09/2026, après coup)

Chaque défaut ci-dessous a d'abord été reproduit par un essai, puis corrigé. Les nouveaux essais (`test_relais_comme_une_connexion_native`,
et la fin de `test_fils_cooperatifs`) ÉCHOUENT sans le correctif (vérifié en remettant l'ancien fichier), et passent avec.
74 tests verts sous les trois bindings. L'application d'essai a été relancée dans Firefox sans interface avec le code corrigé
(« VINGT TICS », « REPONSE 16384 », doublon refusé), ainsi que le lecteur SmartTeacher (scénarios `rendre` et `console` : fini).

| Point | Constat | Suite |
|---|---|---|
| 1. `_actif` / `_suspendus` | Relu scénario par scénario : deux boîtes imbriquées, reprise dans le désordre, exception. Le seul cas où `_actif` pouvait rester vrai à tort (le script principal qui se termine pendant qu'une autre pile attend) est déjà couvert par `lancer`, qui restaure `_actif`. En revanche, **une exception dans un slot reporté** n'allait pas à `sys.excepthook` : asyncio la journalise seulement, alors qu'en natif PyQt appelle le crochet. Une application qui y affiche ses erreurs ne les voyait pas. | corrigé : `_plus_tard` appelle `sys.excepthook`. Établi par lecture du code d'asyncio : la simulation ne peut pas le montrer, car elle passe par PyQt, qui appelle déjà le crochet |
| 2. Relais de `connect` | **Trois défauts confirmés.** (a) Fuite : la table gardait toute lambda connectée, et ce qu'elle capture, après la mort de l'expéditeur. (b) `UniqueConnection` acceptait un doublon, qu'en natif PyQt refuse par `TypeError`. (c) `disconnect()` sans argument laissait des entrées mortes dans la table. `@Slot`, `partial`, les lambdas et `ConnectionType` passent. | corrigé : un relais unique par slot, en référence faible. Plus simple aussi : la boucle de `disconnect_` disparaît |
| 3. `singleShot` doublé | Les formes `(ms, f)`, `(ms, TimerType, f)`, `(ms, receveur, méthode)`, `(ms, signal)` et le receveur détruit avant le coup (rien ne part) se comportent comme en natif. Dans la forme à receveur, le slot est relayé deux fois (par `singleShot` puis par `connect`) : c'est inoffensif. | rien à changer |
| 4. `menu_exec` | Le « un tour après `aboutToHide` » tient, parce que `triggered` part dans le même appel synchrone de Qt. Mais **un menu gardé et réutilisé empilait une connexion `aboutToHide` à chaque `exec()`** (3 après 3 ouvertures). | corrigé : déconnectée à la sortie |
| 5. `fils.py` | `QMutex.lock` (et `lockForRead`/`lockForWrite`) pris deux fois hors entrée suspendable **passait en silence**, alors que la doc et cette note promettaient `RuntimeError`, ce qui n'était vrai que pour `QSemaphore`. `QWaitCondition`, `QSemaphore` et `wait()` sont conformes. | corrigé (`_obtenir`) ; doc précisée (3.6) |
| 6. Fidélité de la simulation | La simulation fait bien mentir `can_run_sync` comme dans le navigateur, et refuse un `run_sync` hors entrée promettante (`assert`). Ce qu'elle ne reproduit pas : le traitement des exceptions par asyncio (point 1) et l'ordre exact des reprises. | laissé, limite dite |

## 10. La page de lancement d'un script quelconque (27/09/2026, demande de l'utilisateur)

Demande : une page qui exécute n'importe quel script, ouvert du disque ou par une URL (`.py`, ou `.zip` d'un module avec
`__main__`), avec en option un fichier passé en argument ; le tout sur le site de qtpy6, et nommé qtpy6.

Livré :
  - `hebergement/index.html` (racine du site) : choix du script et du fichier, ou `?script=URL&fichier=URL` (`fichier`
    répétable) ; une adresse `github.com/…/blob/…` ramenée à `raw.githubusercontent.com` ; une adresse sans extension
    reconnue zip par sa signature `PK`. L'adresse se met à jour pour être partagée quand tout vient d'URL.
  - `hebergement/cadre.html` : où tourne le script, `<iframe sandbox="allow-scripts allow-downloads">` SANS
    `allow-same-origin`. **Choix central** : `smartaudiotools.github.io` est une seule origine pour toutes les Pages du
    compte ; un script venu d'une URL quelconque, exécuté dans la page, lirait le stockage des autres (copies d'élèves).
    Écartés : un simple avertissement avant exécution (on clique « Continuer » sans lire), une organisation GitHub ou un
    domaine à part (possible, mais un compte ou un domaine à gérer, et l'adresse change).
  - `qtpy6/web/lanceur.py` : `point_d_entree` (ordre : `__main__.py` racine, `paquet/__main__.py` par `-m`,
    `paquet/paquet.py` ou `nom_du_zip.py`, le seul `.py` ; un dossier enveloppe sans `__init__.py` est traversé, le
    `__MACOSX` ignoré ; ambiguïté départagée par le nom du zip, sinon erreur) et `executer`.
  - `lancer(..., module=None)` : `python -m paquet` imité par `runpy.run_module` depuis le dossier parent, sinon les
    imports relatifs du `__main__.py` échouent (vérifié : le test échoue sans).
  - `hebergement/construire_site.py` : assemble le site en bibliothèque standard seule (l'action n'a pas Qt ; `assembler`
    importerait qtpy6, donc un binding). `pages.yml` l'appelle et se déclenche aussi sur `qtpy6/**` (le site sert une
    copie du paquet, `qtpy6.zip`).
  - `sonde` sert désormais avec `Access-Control-Allow-Origin: *` : le cadre à origine opaque charge TOUT en CORS
    (y compris ses propres fichiers) ; sans l'en-tête, rien ne se charge (mesuré), GitHub Pages l'envoie.

Niveau de preuve : testé dans Firefox sans interface (sonde) :
  - cadre isolé : `localStorage`, `document.cookie`, `parent.localStorage` → `SecurityError`, origine `null` ; Worker
    par Blob, exec() suspendu, pompe (3 µs) fonctionnent ;
  - `.py` + fichier en argument → `argv` et contenu lus, état `termine` ;
  - zip « Download ZIP » (`depot-main/monpaquet/__main__.py`, import relatif) → `-m monpaquet`, `termine` ;
  - 404 et zip sans point d'entrée → erreur lisible dans la barre (dernière ligne de la trace), journal ouvert ;
  - captures de l'accueil, d'une application en cours et d'une erreur regardées.
  Tests natifs : `test_point_d_entree`, `test_lanceur_zip_de_paquet` (76 tests, PyQt6 et PySide6).
  Jamais essayé : le vrai site en ligne (Pages de qtpy6 non publiées), Chrome, Safari, un téléphone ; le presse-papiers
  (`allow="clipboard-read; clipboard-write"` posé, non mesuré).

À vérifier par un relecteur : que rien dans le cadre ne puisse atteindre la page parente autrement que par `postMessage`
(la page n'écoute que `cadre.contentWindow` et n'exécute rien de ce qu'il envoie : elle affiche du texte par
`textContent`) ; que `allow-downloads` sans `allow-popups` suffit à `stockage.telecharger`.
